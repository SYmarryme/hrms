# CR-DEPLOY-COOKIE-001：部署入口 Cookie 属性兼容性

**状态：DRAFT / NOT_APPROVED。仅供决策；不修改批准设计，不授权迁移或部署。**
关联 T-004、当前入口 T004-05 BLOCKED。依据为用户回传的脱敏属性转换，
以及 2026-10-25 官方公开资料核查；详情见 [平台兼容性结论](t004-platform-compatibility.md)。

问题：Vite 发出的 Path=/api/v1/poc/、SameSite=Lax，在公网收到/存储为 Path=/、SameSite=None。
当前入口不能证明批准的会话/Cookie 安全要求成立。应用端补发、编码 Cookie、改为宽 Path/
SameSite=None、关闭 Host、换成本地存储长期 Token 都不是被批准的解决方法。

| 候选 | 改动与收益 | 前置条件/代价 |
|---|---|---|
| A：厂商受支持的透传配置/入口 | 仅变更平台入口设置，保留当前 CloudStudio 工作流 | 需要官方文档/支持答复和真实 A/B + Chromium PASS；目前未取得 |
| B：开发环境保留 CloudStudio，验证/部署使用可控 Ubuntu HTTPS 单入口 | 自己控制 TLS/响应头，后端 loopback、SQLite 文件和持久化方案延续 | 增加主机/域名/证书、备份与运维责任；课程部署地点需确认；需正式批准后实施 |
| C：继续使用当前会改写的入口并放宽安全要求 | 不符合现有批准安全契约 | 拒绝作为通过验收的方法 |

建议：先补直连 A/B 证据并向厂商确认 A；无受支持且可验证的方法时选择 B 的正式评审。
这不是要求现在购买任何服务，亦不承诺某个未测试平台一定兼容。

不变约束：单一同源 HTTPS 入口、8000 不独立公开、服务端可撤销会话、Secure/HttpOnly/
批准的 SameSite/Path/CSRF、真实权限规则、SQLite 文件/完整性与备份、防回退信任门槛。
不迁移成另一种数据库、不开发员工/工资、不把测试 Cookie 当生产凭据。

受控边缘可采用现有架构已提到的 Nginx/Caddy 类方案，但须独立验证，不承诺仅安装代理即可安全。
例如 [Nginx 官方 proxy_cookie_path/proxy_cookie_flags](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)
说明这些重写指令可显式关闭；仍须核对真实生效配置和最终客户端响应。
若代理仍位于会改写 Cookie 的平台网关之后，仅修改内部 Nginx 不能控制外部那一跳。
